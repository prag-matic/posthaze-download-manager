# Research: `misterdownloadmanager` vs. Posthaze Browser Extension & Bridge Comparison

> **Scope:** Primary-source architectural and implementation comparison between `misterdownloadmanager` ([`anefzaoui/misterdownloadmanager`](https://github.com/anefzaoui/misterdownloadmanager), `main` @ [`828ab8c`](https://github.com/anefzaoui/misterdownloadmanager/tree/828ab8cedd3c059cbd4d564a4a3e6a8ff062f608), workspace v0.5.2) and Posthaze Download Manager (`extensions/chrome` + `posthaze-cli` + `posthaze-ui`, v0.2.1).
> **Focus Areas:** Manifest V3 permissions & browser targets, download interception & race handling, session header/cookie/referer/redirect capture, user-facing extension UX, Native Messaging & desktop IPC transport, and prioritized improvements (`P0`–`P2` plus `What Not to Adopt / Keep Ours`).
> **Non-goal:** No application or extension source code (`crates/`, `extensions/`) is modified by this document. Every factual claim cites verified file paths, line ranges, and symbol names from both repositories.

---

## 1. Executive Summary & Architectural Contrast

Both extensions use Manifest V3 and Chromium Native Messaging to hand downloads—along with authenticated browser context—to a Rust desktop application, yet they sit at very different points on the simplicity-vs.-coverage spectrum:

- **Posthaze (`extensions/chrome/`, ~625 LOC JS/HTML + ~810 LOC Rust host/IPC):** Prioritizes **minimal permission footprint, zero content-script overhead, and clean MV3 modularity** (`type: "module"` service worker + pure-function `headers.js` with Node unit tests). It already solves **CHIPS partitioned cookies** (`partitionKey: { topLevelSite }`), **active-tab `Referer` fallback**, **signed single-use URL hints** (`expiry` + `mac` -> `singleStream` / `skipProbe`), **1-click HKCU registration inside desktop Settings**, and **headless SQLite staging** when the UI is closed. Its main gaps are **late `downloads.onCreated` interception** (instead of `onDeterminingFilename` in Chromium), **ephemeral in-memory `bypassedUrls` state** in the service worker, **missing incognito `storeId` isolation**, **manual 32-char Extension ID copy-paste** (no pinned `"key"` in `manifest.json`), and **limited popup/context-menu ergonomics** (no `Alt+Click` bypass, no page link grabber, no `POST` form replay, no per-site popup toggle).
- **`misterdownloadmanager` (`extension/` + `crates/nmhost` + `crates/ipc`, ~5,200 LOC core JS + ~4,700 LOC Rust host/IPC):** Optimizes for **browser parity across Chromium, Firefox, and Safari** and **zero-friction edge-case handling** (Cloudflare `Alt+Click` bypass, `onDeterminingFilename` pre-allocation pause, `declarativeNetRequest` inline PDF/media capture, `POST` form body replay, redirect-chain origin tracking, `AllowSetForegroundWindow` focus handoff, persistent `connectNative` popup port, and `"key"`-pinned unpacked extension IDs alongside Web Store IDs). However, much of its complexity stems from features Posthaze deliberately scopes out (in-page `video.js` yt-dlp overlay, Web Store review workarounds, Safari appex, and a separate LAN HTTPS server).

## 2. Manifest V3 Permissions, Browser Targets & Security Surface

### 2.1 Manifest Permissions & API Footprint

- **Posthaze (`extensions/chrome/manifest.json`):**
  - Declares `manifest_version: 3`, `background.service_worker: "service-worker.js"` with `"type": "module"`, and `action.default_popup: "popup.html"` ([manifest.json#L1-L34](file:///e:/Development/posthaze-download-manager/extensions/chrome/manifest.json#L1-L34)).
  - **Permissions (5):** `downloads`, `nativeMessaging`, `cookies`, `contextMenus`, `storage` ([manifest.json#L12-L18](file:///e:/Development/posthaze-download-manager/extensions/chrome/manifest.json#L12-L18)).
  - **Host permissions:** `<all_urls>` ([manifest.json#L19-L21](file:///e:/Development/posthaze-download-manager/extensions/chrome/manifest.json#L19-L21)) — required so `chrome.cookies.getAll({ url })` can read session cookies for arbitrary download origins.
  - **Gap — Missing `tabs` permission:** `headers.js` calls `chromeApi.tabs.query({ active: true, lastFocusedWindow: true })` to read `tabs[0].url` as a `Referer` / `topLevelSite` fallback ([headers.js#L22-L24](file:///e:/Development/posthaze-download-manager/extensions/chrome/headers.js#L22-L24)). Without `"tabs"` in `manifest.json`, `tab.url` returns `undefined` unless granted implicitly (see [`chrome-extensions` MV3 Rule 4](C:/Users/prage/.gemini/config/plugins/modern-web-guidance-plugin/skills/chrome-extensions/SKILL.md#L82-L85)), although `<all_urls>` in `host_permissions` does expose `tab.url` in Chromium MV3 for matching HTTP/HTTPS origins. Declaring `"tabs"` explicitly—or verifying reliance on `<all_urls>`—makes the contract unambiguous across Chromium/Firefox variants.
  - **Zero content scripts:** No `content_scripts` and no `scripting` / `webRequest` permissions; smallest possible attack surface on visited pages.

- **`misterdownloadmanager` (`extension/manifest*.json`):**
  - Ships three target manifests built from one shared codebase via [`tools/extension/pack.ps1`](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/tools/extension/pack.ps1#L22-L67):
    1. **Chromium (`extension/manifest.json`):** `minimum_chrome_version: "116"`, pins a deterministic RSA public `"key"` for unpacked installs (`UNPACKED_ID = "oogbclbbninliongijffeeggalppliok"`, stripped by `pack.ps1#L50` for the Chrome Web Store zip whose signed ID is `STORE_ID = "ejoleppdfgjdndddcjoehopknmlglojp"`), and requests **9 permissions**: `downloads`, `contextMenus`, `nativeMessaging`, `cookies`, `storage`, `webRequest`, `scripting`, `declarativeNetRequestWithHostAccess`, `proxy`, plus `host_permissions: ["<all_urls>"]` ([manifest.json#L1-L23](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/manifest.json#L1-L23), [extension.rs#L6-L10](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/ipc/src/extension.rs#L6-L10)).
    2. **Firefox (`extension/manifest.firefox.json`):** Adds `browser_specific_settings.gecko` (`id: "integration@misterdownloadmanager.com"`, `strict_min_version: "140.0"`, `data_collection_permissions.required: ["none"]`), uses `background.scripts: ["background.js"]` (MV3 event page), swaps `declarativeNetRequestWithHostAccess` for `webRequestBlocking`, and moves `proxy` to `optional_permissions` ([manifest.firefox.json#L8-L39](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/manifest.firefox.json#L8-L39)).
    3. **Safari (`extension/manifest.safari.json`):** `strict_min_version: "17.0"`, omits `downloads` and `proxy` completely (`background.persistent: false`) ([manifest.safari.json#L7-L23, #L60-L64](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/manifest.safari.json#L7-L23)).
  - **Content scripts in all frames:** Injects `video.js` (`document_idle`) and `page.js` (`document_start`) into `<all_urls>` with `all_frames: true`, re-injecting on `onInstalled` via `chrome.scripting.executeScript` ([manifest.json#L35-L56](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/manifest.json#L35-L56), `injectOpenTabs()` at [background.js#L3230-L3248](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L3230-L3248)).

### 2.2 Security Surface & Boundary Checks

- **Extension ID Pinning & Origin Allowlist:**
  - Posthaze generates `allowed_origins: ["chrome-extension://<user_pasted_id>/"]` dynamically ([browser_integration.rs#L62-L76](file:///e:/Development/posthaze-download-manager/crates/posthaze-ui/src/browser_integration.rs#L62-L76)). This forces every unpacked install user to manually copy-paste their locally generated ID, though `format_extension_origin()` accepts arbitrary `[A-Za-z0-9_-]` rather than strictly 32 `[a-p]` characters ([browser_integration.rs#L47-L52](file:///e:/Development/posthaze-download-manager/crates/posthaze-ui/src/browser_integration.rs#L47-L52)).
  - MDM embeds `"key"` in `extension/manifest.json#L9`, giving **every unpacked developer/user install the identical deterministic ID** `oogbclbbninliongijffeeggalppliok`. Its `nmhost` validates `valid_id()` (`len == 32 && bytes.all(|b| b'a'..=b'p')`, [extension.rs#L29-L31](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/ipc/src/extension.rs#L29-L31)) and additionally enforces `our_caller()` against CLI args passed by the browser ([nmhost/src/main.rs#L1433-L1437](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/nmhost/src/main.rs#L1433-L1437)).
- **Sender & URL Validation:**
  - Posthaze checks `url.starts_with("http://") || url.starts_with("https://")` in JS ([service-worker.js#L136, #L192](file:///e:/Development/posthaze-download-manager/extensions/chrome/service-worker.js#L136)), `native_host.rs#L164`, and `ipc.rs#L125`. However, `service-worker.js` `onMessage` does **not** check `sender.id === chrome.runtime.id` (relies on no `externally_connectable`, which is safe by default in MV3).
  - MDM explicitly verifies `sender.id !== ext.runtime.id` and separates extension pages (`sender.url.startsWith(ext.runtime.getURL(""))`) from web content scripts (`fromPage`, [background.js#L3678-L3683](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L3678-L3683)). It also calls `siteAccess(first)` (`ext.permissions.contains({ origins: [...] })`) so if a user set Chrome's site access to *"On click"* or *"On specific sites"*, MDM leaves the download to the browser rather than silently dropping session cookies ([background.js#L2126-L2134, #L2489](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L2126-L2134)).
- **Private / Incognito Leakage:**
  - Posthaze does **not** track `item.incognito` or `item.cookieStoreId`. If the extension is enabled in Incognito ("Allow in Incognito"), `headers.js` queries `chrome.cookies.getAll({ url })` (default non-incognito store `"0"`!) and forwards regular-profile cookies onto an incognito download—or fails to grab incognito cookies—and writes `lastStatus.url` persistently into `chrome.storage.local` ([service-worker.js#L101-L108](file:///e:/Development/posthaze-download-manager/extensions/chrome/service-worker.js#L101-L108)).
  - MDM passes `private: Boolean(incognito)`, omits `name`/`site` from `chrome.storage.local.declined` and from `mdm.log` when `private` is true ([background.js#L760-L766](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L760-L766), [nmhost/src/main.rs#L577-L594](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/nmhost/src/main.rs#L577-L594)), and queries `storeId: "1"` in Chrome incognito ([background.js#L2050-L2057](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L2050-L2057)).
- **MV3 Compliance Note:**
  - Posthaze violates MV3 ephemeral service-worker hygiene in one place: `const bypassedUrls = new Map()` ([service-worker.js#L151](file:///e:/Development/posthaze-download-manager/extensions/chrome/service-worker.js#L151)) is stored only in memory (though its 15s window mitigates SW termination unless the fallback triggers a slow navigation). MDM stores `paused`, `rules`, `status`, and `declined` in `chrome.storage.local` and `media` / `running` in `chrome.storage.session` ([background.js#L1311-L1339, #L3689-L3696](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L1311-L1339)), while keeping short-lived 10s–120s correlation maps (`posts`, `redirected`, `bypass`, `startedFrom`, `newTabs`) in memory.

## 3. Download Interception & Edge-Case Handling

### 3.1 Interception Point: `onCreated` vs. `onDeterminingFilename`

- **Posthaze (`chrome.downloads.onCreated`):**
  1. Guards against restored history items via `isFreshActiveDownload(item)` (`state === "in_progress"`, `!paused`, `!endTime`, `startTime` within `STALE_DOWNLOAD_AGE_MS = 60_000` ms) ([service-worker.js#L166-L181](file:///e:/Development/posthaze-download-manager/extensions/chrome/service-worker.js#L166-L181)).
  2. Checks `interceptEnabled`, HTTP(S) scheme, one-shot `consumeBypassedUrl(url)`, and `shouldSkipDownload(item, url, settings)` ([service-worker.js#L183-L200](file:///e:/Development/posthaze-download-manager/extensions/chrome/service-worker.js#L183-L200)).
  3. Sends a synchronous-feeling **round-trip `{ type: "ping" }`** to `com.posthaze.host` to verify `ping.mode === "pong"` (UI running) ([service-worker.js#L204-L207](file:///e:/Development/posthaze-download-manager/extensions/chrome/service-worker.js#L204-L207)).
  4. **Cancels & erases first**, *then* gathers headers and sends `{ type: "enqueue" }` ([service-worker.js#L210-L227](file:///e:/Development/posthaze-download-manager/extensions/chrome/service-worker.js#L210-L227)).
  - **Race & UX Bugs in `onCreated`:**
    - At `onCreated` time in Chromium, `item.filename` is frequently **still empty `""`** and `item.totalBytes` is often **`-1` or `0`** because `Content-Disposition` / `Content-Length` resolution happens right after `onCreated`, before `onDeterminingFilename`. Consequently, `shouldSkipDownload()` frequently misses extension exclusions when the filename comes from `Content-Disposition` (e.g., `/download?id=123` -> `icon.svg`) and misses `minSizeMb` checks!
    - Because Posthaze cancels/erases *during* `ping` + `enqueue`, Chrome has already started writing to the browser download stream while the `ping` native process spawns, and if `enqueue` fails, Posthaze has to **re-issue a brand-new GET** via `chrome.downloads.download({ url })` ([service-worker.js#L230-L237](file:///e:/Development/posthaze-download-manager/extensions/chrome/service-worker.js#L230-L237))—which breaks `POST` form downloads and burns single-use signed tokens!
    - Also, Posthaze sends **two separate Native Messaging process spawns** (`ping` then `enqueue`) per intercepted download, doubling process-creation latency on Windows.

- **`misterdownloadmanager` (`onDeterminingFilename` on Chromium, `onHeadersReceived` + `onCreated` on Firefox):**
  - **Chromium (`ext.downloads.onDeterminingFilename`):**
    - Fires *after* redirects and `Content-Disposition` / `Content-Length` / `mime` are resolved, and **pauses the download before any file allocation or conflict prompt** as long as the listener returns `true` and calls `suggest(...)` asynchronously ([background.js#L2637-L2650](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L2637-L2650)).
    - **Zero-loss fallback:** If `offer()` returns `false` (app unreachable, rule declined, user paused), MDM simply calls `noName(suggest)` and lets Chrome resume the **exact original request/response stream** untouched—no second GET, no `POST` loss, no `bypassedUrls` hack needed!
    - **Extension-conflict-safe `noName(suggest)`:** Instead of calling `suggest()` with no args (which in Chromium overrides other filename-renaming extensions with an empty name!), MDM calls `suggest({ filename: "..", conflictAction: "uniquify" })` ([background.js#L2610-L2612](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L2610-L2612)), which Chromium rejects and discards as a no-op so other extensions' suggestions survive.
  - **Firefox (`webRequest.onHeadersReceived` + `downloads.onCreated`):**
    - Because Firefox lacks `onDeterminingFilename` and otherwise prompts *"What should Firefox do with this file?"* while downloading in the background, MDM intercepts `onHeadersReceived` in `blocking` mode (`answerFile()`), decides before the dialog appears, returns `{ cancel: true }` if MDM took it, and records `decided` so `downloads.onCreated` does not re-evaluate ([background.js#L2658-L2676, #L2948-L2991](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L2658-L2676)).
  - **Dangling Tab Cleanup (`closeLeftTab` / `closeDownloadTab`):**
    - Tracks `ext.tabs.onCreated` for 10s (`newTabs`); when a download is dropped (`drop(item)`), closes the temporary blank/download tab opened solely for that link ([background.js#L2560-L2599](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L2560-L2599)).

## 4. Session Header, Cookie, Referer & Redirect Capture

### 4.1 Cookies (`cookies` API, CHIPS `partitionKey`, and `storeId`)

- **Posthaze (`extensions/chrome/headers.js`):**
  - **Strength — CHIPS Partitioned Cookies:** `collectCookiesForUrl(url, topLevelSite, cookiesApi)` ([headers.js#L30-L58](file:///e:/Development/posthaze-download-manager/extensions/chrome/headers.js#L30-L58)) queries `cookies.getAll({ url })` **and** `cookies.getAll({ url, partitionKey: { topLevelSite } })` (verified by unit tests in [headers.test.js#L6-L151](file:///e:/Development/posthaze-download-manager/extensions/chrome/headers.test.js#L6-L151)), deduplicating by `cookie.name`. This directly fixes third-party CDN downloads protected by CHIPS (e.g., Cloudflare `cf_clearance` partitioned under `topLevelSite`).
  - **Gap — No `storeId` / Incognito Isolation:** Always omits `storeId`, so incognito downloads read the default cookie jar (`"0"`).
  - **Gap — Flat `Cookie` header string only:** Formats `name=value; ...` once for the download URL. On cross-host redirects during download, Posthaze sends the same `Cookie` string to the final host (unlike MDM's `cookieJar` + `scoped_headers`).

- **`misterdownloadmanager` (`extension/background.js`):**
  - **Strength — `storeId` + Full `cookieJar` + `webRequest` fallback:**
    - `cookiesFor(url, { incognito, storeId })` passes `storeId` (Firefox containers/private windows) or `storeId: "1"` (Chrome incognito) ([background.js#L2050-L2057](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L2050-L2057)).
    - For media/yt-dlp, `videoCookies()` serializes full `BrowserCookie` objects (`domain`, `hostOnly`, `path`, `secure`, `expirationDate`) into `cookieJar`, and `streamContext()` merges any frame-partitioned `Cookie`/`Referer`/`Origin` headers observed via `webRequest.onSendHeaders` with `["requestHeaders", "extraHeaders"]` ([background.js#L1233-L1261, #L2071-L2122](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L1233-L1261)).
  - **Weakness — No `partitionKey` on `cookies.getAll`:** MDM does *not* pass `partitionKey: { topLevelSite }` in `cookiesFor()` ([background.js#L2052](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L2052)), so regular file handoffs (which don't use `streamContext`) miss CHIPS-partitioned cookies on Chromium! **Posthaze is already ahead here.**

### 4.2 Referer, `pageUrl`, `User-Agent`, Redirects, and `POST` Forms

- **`Referer` & `pageUrl`:**
  - Posthaze uses `item.referrer` if HTTP(S), falling back to `tabs.query({ active: true, lastFocusedWindow: true })` ([headers.js#L16-L28, #L69-L75](file:///e:/Development/posthaze-download-manager/extensions/chrome/headers.js#L16-L28)), and sends `User-Agent` from `navigator.userAgent`. On context-menu clicks, it passes `info.pageUrl || tab.url` and `topLevelUrl: tab.url || info.pageUrl` ([service-worker.js#L139-L142](file:///e:/Development/posthaze-download-manager/extensions/chrome/service-worker.js#L139-L142)).
  - **Why `item.referrer` + `activeTab` isn't always enough:** When a link opens in a new background/popup tab that auto-closes upon download start, or when `Referrer-Policy: strict-origin-when-cross-origin` strips the path to `https://site.com/`, the full source page URL is lost. - **Redirect URLs (`url` vs. `finalUrl`):**
  - Posthaze collapses `const url = item.finalUrl || item.url || ""` ([service-worker.js#L191](file:///e:/Development/posthaze-download-manager/extensions/chrome/service-worker.js#L191)), discarding `item.url`. If `item.url` was a thank-you page redirect or a stable permalink redirecting to a short-lived CDN URL, Posthaze loses the distinction; conversely, MDM sends *both* `url: firstUrl(item)` and `finalUrl`, using `loadedPages` (`text/html` 200 responses, 120s TTL) to avoid treating a thank-you HTML page (`location.href = installer.exe`) as `firstUrl` ([background.js#L917-L924, #L1274-L1280](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L917-L924)).
- **`POST` Form Downloads:**
  - Posthaze assumes every download is a `GET`. MDM captures `webRequest.onBeforeRequest` (`["requestBody"]`) + `onBeforeSendHeaders` (`Content-Type`) for 120s (`BODY_LIMIT = 512 KiB`) and either replays `application/x-www-form-urlencoded` / UTF-8 raw text bodies (`post`, `postType`) or leaves `multipart`/binary uploads to the browser ([background.js#L787-L893](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/extension/background.js#L787-L893)).
- **Signed-Link Optimization (Posthaze Advantage):**
  - Posthaze's `buildEnqueueHints()` ([headers.js#L96-L121](file:///e:/Development/posthaze-download-manager/extensions/chrome/headers.js#L96-L121)) detects `expiry` + `mac` query parameters (or configured `singleStreamDomains`) and forwards `totalBytes`, `singleStream: true`, and `skipProbe: true` straight into `DownloadRequest` ([native_host.rs#L186-L192](file:///e:/Development/posthaze-download-manager/crates/posthaze-cli/src/native_host.rs#L186-L192), [main.rs#L685-L690](file:///e:/Development/posthaze-download-manager/crates/posthaze-ui/src/main.rs#L685-L690)), preventing `HEAD` probes or multi-connection bursts from invalidating single-use signed URLs.

### 6.2 Native Messaging Framing & Host Loop

- **Posthaze (`crates/posthaze-cli/src/native_host.rs`):**
  - Implements `read_frame` / `write_frame` with 4-byte LE `u32` framing and `MAX_FRAME_BYTES = 1 MiB` ([native_host.rs#L20, #L76-L105](file:///e:/Development/posthaze-download-manager/crates/posthaze-cli/src/native_host.rs#L20)).
  - **Single-message exit:** `run_native_host` reads **one** frame from `stdin`, processes it, writes **one** `NativeResponse`, and exits (`while` loop absent) ([native_host.rs#L107-L142](file:///e:/Development/posthaze-download-manager/crates/posthaze-cli/src/native_host.rs#L107-L142)). That matches `chrome.runtime.sendNativeMessage` (one-shot), though it cannot serve persistent `chrome.runtime.connectNative` ports without adding a `while let Some(...)` loop.
  - **Subtle error-handling edge case:** If `resp.ok` is `false` (for example, validation error or pipe receiver closed), `run_native_host` returns `ExitCode::FAILURE` after writing the JSON response ([native_host.rs#L137-L141](file:///e:/Development/posthaze-download-manager/crates/posthaze-cli/src/native_host.rs#L137-L141)), which can cause Chromium to reject `sendNativeMessage` with `"Native host has exited."` before the caller inspects `{ ok: false, error }` if stdout closes/flushes tightly with non-zero exit.
  - **Process-launch breakaway:** `launch_ui_process()` sets `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` ([native_host.rs#L261-L267](file:///e:/Development/posthaze-download-manager/crates/posthaze-cli/src/native_host.rs#L261-L267)), **without** `CREATE_BREAKAWAY_FROM_JOB` (`0x0100_0000`). Chromium spawns Native Messaging hosts inside a **Windows Job Object** that kills the entire tree when the native host exits; without `CREATE_BREAKAWAY_FROM_JOB` (with fallback if the job denies breakaway, as MDM does at [nmhost/src/main.rs#L1296-L1306](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/nmhost/src/main.rs#L1296-L1306)), `OPEN POSTHAZE` (`show_ui` when UI is closed) can be killed by Chrome/Edge right after `posthaze-cli.exe` exits!

- **`misterdownloadmanager` (`crates/nmhost/src/main.rs`):**
  - Loops `while let Some(raw) = read_message(&mut stdin)?` ([nmhost/src/main.rs#L1326](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/nmhost/src/main.rs#L1326)), supporting both one-shot `sendNativeMessage` and persistent `connectNative` ports (`hostAsk()` for popup live downloads).
  - If an incoming frame exceeds `MAX_MESSAGE` (`1 MiB`), drains the oversized frame (`io::copy` to `io::sink()`) and replies `{"ok": false, "why": "too-large"}` rather than crashing or hanging the pipe ([nmhost/src/main.rs#L1093-L1096, #L1329-L1336](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/nmhost/src/main.rs#L1093-L1096)).
  - **Windows Foreground Lock Handoff (`AllowSetForegroundWindow`):** Because Chrome is the foreground process when spawning `nmhost`, Windows blocks background `posthaze-ui.exe` / `misterdownloadmanager.exe` from stealing focus unless the foreground-owning process calls `AllowSetForegroundWindow(pid)`. MDM reads `pid` from `ipc.json` (or `child.id()` on launch) and calls `AllowSetForegroundWindow(pid)` right before delivering commands ([nmhost/src/win32.rs#L9-L15](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/nmhost/src/win32.rs#L9-L15), [nmhost/src/main.rs#L1217-L1219, #L1255-L1256](C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/nmhost/src/main.rs#L1217-L1219)). Posthaze has no `AllowSetForegroundWindow` call in `native_host.rs`, so `PreflightWindow` or `ShowMainWindow` can flash in the taskbar behind Chrome instead of activating reliably.

**Transport Takeaway:** Posthaze's **Windows Named Pipe (`\\.\pipe\posthaze-browser-bridge`)** is fundamentally cleaner and more secure on Windows than loopback TCP (`ipc.json`)—browsers and web pages cannot connect to `\\.\pipe\*`, eliminating CSRF, HTTP-smuggling, and port-probing threats entirely—**and** Posthaze's headless SQLite staging (`queued-headless`) avoids spawning a full GPU/GPUI window just to queue a context-menu link. However, Posthaze can adopt MDM's `AllowSetForegroundWindow`, `CREATE_BREAKAWAY_FROM_JOB`, direct binary invocation (dropping the `.cmd` shim), and single-request `enqueue` without a redundant `ping` subprocess.

### What Not to Adopt / Keep Ours

1. **Keep Posthaze's Windows Named Pipe (`\\.\pipe\posthaze-browser-bridge`) — do NOT adopt MDM's Loopback TCP + `ipc.json` token server.**
   - *Why:* Named Pipes cannot be dialed by browser `fetch()`/XHR/WebSockets, completely eliminating CSRF, DNS-rebinding, and port-scanning surfaces that forced MDM to implement `looks_like_http()`, constant-time bearer tokens, and `MAX_IN_FLIGHT` throttling.
2. **Keep Posthaze's CHIPS Partitioned Cookie (`partitionKey: { topLevelSite }`) lookup in `headers.js` — MDM lacks this.**
   - *Why:* `headers.js` already merges unpartitioned and CHIPS-partitioned cookies with unit tests ([headers.test.js](file:///e:/Development/posthaze-download-manager/extensions/chrome/headers.test.js)), which handles modern Chromium third-party CDN cookies better than MDM's `cookiesFor()`.
3. **Keep Posthaze's Signed-URL Hinting (`buildEnqueueHints` for `expiry`+`mac` / `singleStreamDomains`) & Headless SQLite Staging (`queued-headless`).**
   - *Why:* Avoiding `HEAD` probes and multi-stream bursts on signed URLs prevents burning one-time tokens, and staging context-menu links into `state.db` (`enqueue_paused`) when the UI is closed avoids launching a heavyweight GPU window in the background.
4. **Do NOT adopt MDM's `video.js` (2,957 LOC in-page yt-dlp DOM overlay), `crates/remote` LAN HTTPS server, or Safari `.appex` wrapper unless Posthaze explicitly expands scope to `yt-dlp`/macOS/LAN control.**
   - *Why:* Injecting a 157 KiB shadow-DOM content script into every frame on `<all_urls>` dramatically increases page-breakage risk, Web Store review complexity (note MDM even keeps `videoKeptOff()` / `exclude_matches` support in `background.js#L3218-L3226` for store policy constraints), and maintenance burden outside Posthaze's core HTTP/HTTPS download manager mission.
5. **Keep Posthaze's lean blocklist (`excludedExtensions` / `excludedDomains` / `minSizeMb`) over MDM's 200-extension hardcoded allowlist — just add sensible default exclusions (`crx`, `xpi`, `html`, `htm`) once switching to `onDeterminingFilename`.**
   - *Why:* A blocklist captures modern/unlisted file formats (e.g., `.gguf`, `.safetensors`, `.zst`, `.whl`) automatically without shipping migration code (`EARLIER_AUTO_TYPES`) whenever new extensions emerge.
