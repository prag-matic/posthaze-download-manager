# Research: `misterdownloadmanager` (`mdm-engine`) vs. Posthaze (`posthaze-engine`) Engine Comparison

> **Scope:** Primary-source architectural and implementation comparison between `misterdownloadmanager` (`mdm-engine` / `mdm-app`, v0.5.2) and Posthaze Download Manager (`posthaze-engine` / `posthaze-ui`, v0.2.1), focused on **download connection handling**, **worker orchestration**, **throughput & disk I/O**, and **areas where Posthaze is already stronger**.
> **Non-goal:** No application source code (`crates/`, `Cargo.toml`) is modified by this document. Every recommendation includes an explicit throughput/complexity assessment grounded in exact source lines from both codebases.

---

## 1. Executive Summary & Prioritized Improvements

Both engines are pure-Rust, Tokio + `reqwest`/`rustls` multi-segment HTTP/HTTPS download managers, yet they optimize for markedly different bottlenecks:

- **`posthaze-engine`** excels at **structural leanness, bounded memory, and crash-safe persistence**: it uses a single dedicated blocking `PartFileWriter` with a fixed `16 MiB` (`32 × 512 KiB`) recycled `ChunkBufferPool`, single-syscall `FileExt::seek_write` on Windows, a bounded Tokio runtime (`2..=4` workers), and SQLite WAL checkpoints with `PRAGMA shrink_memory`.
- **`mdm-engine`** excels at **real-world internet resilience, tail-latency elimination, and Windows NTFS edge cases**: it avoids `HEAD` probe RTTs by streaming byte `0` from the initial `GET`, sets `FSCTL_SET_SPARSE` before `set_len()` on Windows NTFS (preventing multi-second zero-fill stalls), detects and reconnects slow/stalled workers (`should_shed` + `read_timeout`), isolates individual worker failures, honors `Retry-After` on `429`/`503`, learns per-host connection caps (`HostLimits`), races multi-IP DNS endpoints (`RFC 8305`-style Happy Eyeballs), and validates mid-transfer/resume ranges with strong `If-Range` and 64-byte overlap checks.

### Prioritized Adoption Matrix for Posthaze

| Priority | Improvement | Primary Subsystem | Expected Impact | Complexity / Risk |
|---|---|---|---|---|

| **P1** | Enforce `.http1_only()` explicitly in `build_http_client()` + add preflight disk-space & FAT32 `4 GiB - 1` check | Connection / Disk (`lib.rs`, `runner.rs`) | **Prevents accidental HTTP/2 multiplexing** if a crate enables `reqwest/http2`, and fails fast before allocating | **Low** (`GetDiskFreeSpaceExW` / `GetVolumeInformationByHandleW` already align with Posthaze's `windows-sys` setup) |
| **P2** | Send `If-Range` on segment requests (strong ETag / `Date >= Last-Modified + 1s`) + 64-byte resume overlap check | Integrity / Resume (`transfer.rs`, `runner.rs`) | **Prevents silent file corruption** if a remote file rotates mid-transfer or lacks validators on resume | **Low–Medium** (read 64 bytes via `seek_read` before writing resumed segment) |
| **P2** | Add learned per-host connection caps (`HostLimits`) with TTL decay | Connection / Retries (`lib.rs`, `transfer.rs`) | **Avoids wasted retry loops & bans** on servers capping concurrency below `max_workers` (e.g. 2–4 conns) | **Low** (small `Mutex<HashMap<String, Learned>>` on `DownloadEngine`) |
| **P2** | Upgrade `BandwidthLimiter` with immediate `Notify` wakeup on dynamic rate increase & `refund()` on trimmed/aborted chunks, removing the `5 ms` sleep floor | Speed / Throttling (`throttle.rs`) | **Eliminates sleep overshoot** when raising/removing speed limits live or under bursty high caps | **Low** (mirror `mdm-engine/src/limiter.rs` era/mark design) |
| **P3** | Add RFC 8305-style staggered TCP connect race (`250 ms` stagger, `300 s` winner cache) + `tls-native-roots` / platform verifier option for enterprise MITM proxies | DNS / TLS (`lib.rs`) | **Eliminates 15 s dead-IP stalls** on dual-stack hosts and fixes corporate/AV root-cert errors | **Medium** (custom `reqwest::dns::Resolve` impl) |

## 3. Deep Comparison: Download Connection Handling

### 3.1 HTTP Client Setup, Protocol Version, and Connection Pooling

- **`misterdownloadmanager`:**
  - `client_with()` ([crates/engine/src/download.rs#L1976-L2144](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L1976-L2144)) explicitly forces `.http1_only()` ([download.rs#L2136](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L2136)) so every concurrent worker maps to an independent TCP socket rather than multiplexing over a single HTTP/2 connection.
  - Configures `.connect_timeout(opts.connect_timeout)` (default `30s`, [download.rs#L279, #L2138](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L279)), **`.read_timeout(opts.read_timeout)`** (default `30s`, [download.rs#L280, #L2139](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L280)), `.pool_max_idle_per_host(opts.connections() as usize)` ([download.rs#L2140](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L2140)), `.pool_idle_timeout(POOL_IDLE)` (`15s`, [download.rs#L1963, #L2141](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L1963)), and `.tcp_nodelay(true)` ([download.rs#L2142](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L2142)).
  - **Trade-off:** Building a fresh `reqwest::Client` per download in MDM discards warm keep-alive sockets and TLS sessions between sequential downloads to the same host (and re-runs `tls::configure`).
  - When falling back to its `wreq` BoringSSL browser-emulation client (which speaks HTTP/2), MDM uses a `Lease` + `wreq::Group` pool partition ([crates/engine/src/browserlike.rs#L79-L111](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/browserlike.rs#L79-L111), [browserlike.rs#L699-L724](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/browserlike.rs#L699-L724)) so concurrent workers still open distinct TCP connections instead of sharing one HTTP/2 stream!
- **`posthaze-engine`:**
  - `build_http_client()` ([crates/posthaze-engine/src/lib.rs#L683-L711](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/lib.rs#L683-L711)) shares one `reqwest::Client` across the engine (preserving warm TLS/keep-alive pools across downloads and only rebuilding on proxy changes at [lib.rs#L509-L530](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/lib.rs#L509-L530)).
  - Currently avoids HTTP/2 implicitly because workspace `Cargo.toml#L18` configures `reqwest = { version = "0.12", default-features = false, features = ["rustls-tls", "stream"] }` without `http2` (verified in [Cargo.lock#L6236-L6274](file:///e:/Development/posthaze-download-manager/Cargo.lock#L6236-L6274)), though `build_http_client()` does **not** call `.http1_only()` explicitly (so enabling `reqwest/http2` anywhere in the dependency graph would silently collapse multi-worker downloads onto one TCP socket).
  - **Gap — No `read_timeout`:** `build_http_client()` sets `.connect_timeout(Duration::from_secs(15))`, `.pool_max_idle_per_host(6)`, `.pool_idle_timeout(Duration::from_secs(30))`, and `.tcp_nodelay(true)` ([lib.rs#L686-L689](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/lib.rs#L686-L689)), **but omits `.read_timeout(...)`**. In `run_segment_attempt()` ([transfer.rs#L639](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L639)) and `stream_unbounded_to_writer()` ([transfer.rs#L816](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L816)), `stream.next().await` has no idle socket timeout and can stall indefinitely if a server or NAT drops packets mid-transfer without a TCP FIN/RST.

### 3.2 Probing Strategy & Startup Latency

- **`misterdownloadmanager` (Zero-Waste Probe):**
  - Instead of `HEAD` + `Range: bytes=0-0`, MDM's first request is a **plain `GET` (no `Range`)** in `run_fresh()` / `probe_kept()` ([crates/engine/src/download.rs#L982-L1155](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L982-L1155), [download.rs#L2231-L2280](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L2231-L2280)).
  - That open `Response` body becomes Worker `0`'s stream starting at byte `0` (`KeptAnswer` if probed earlier by the info dialog within `KEEP_ANSWER_FOR = 15 min`, [download.rs#L944-L978, #L2253-L2266](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L944-L978)). Range support is learned dynamically when Workers `1..N` send `Range` requests: `206` confirms ranges (`RANGES_YES`); `200` flips `RANGES_NO`, and `Planner::absorb_next(0)` / `make_single(0)` lets Worker `0` keep streaming seamlessly from byte `0` without reopening the connection ([crates/engine/src/planner.rs#L294-L325](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/planner.rs#L294-L325), [download.rs#L4346-L4356, #L5575-L5589](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L4346-L4356)).
  - Benefits: Saves 1–2 RTTs on startup and avoids servers that block `HEAD` or invalidate single-use signed URLs after `HEAD` / `bytes=0-0`.
- **`posthaze-engine` (Two-Step Probe):**
  - `probe_url_with_headers()` ([crates/posthaze-engine/src/probe.rs#L51-L96](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/probe.rs#L51-L96)) sends `HEAD` first; if `HEAD` returns `403`/`405`/`501` or omits `Accept-Ranges: bytes` / `Content-Length`, it issues a `GET` with `Range: bytes=0-0` ([probe.rs#L118-L155](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/probe.rs#L118-L155)) and drops the response body. Then `execute_download()` starts workers from scratch. (If `skip_probe` is true, [runner.rs#L206-L219](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/runner.rs#L206-L219) forces `supports_ranges = false`, falling back to single-stream.)
  - When a server answers `200 OK` to a `Range` request after advertising `Accept-Ranges: bytes`, Posthaze cleanly falls back to `execute_single_stream()` ([runner.rs#L408-L454](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/runner.rs#L408-L454)), though it has to reopen a fresh `GET` from byte `0`.

### 3.3 DNS, Happy Eyeballs, TLS, Proxies, and Redirects

- **DNS & Address Racing:**
  - `mdm-engine` wraps lookups in `dns::Resolver` ([crates/engine/src/dns.rs#L583-L768](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/dns.rs#L583-L768)): supports System DNS, Plain TCP DNS, DoT, and DoH via `hickory-resolver`, caps lookup time at `0.9 * connect_timeout` (`lookup_limit`, [dns.rs#L579-L581](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/dns.rs#L579-L581)), and runs an RFC 8305-style staggered TCP connect race (`STAGGER = 250ms`, `RACE_BUDGET = 3s`, winner cached for `REMEMBER = 300s`, [dns.rs#L569-L573, #L702-L768](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/dns.rs#L569-L573)). This avoids hyper's sequential multi-IP connect stalls when an IPv6 or first A record is unreachable.
  - `posthaze-engine` uses `reqwest`'s default system resolver (`GaiResolver`) without address racing or winner caching.
- **TLS Root Trust & Diagnostics:**
  - `mdm-engine` configures `rustls` (`aws-lc-rs`) with `rustls-platform-verifier` **merged** with Mozilla's unconstrained `webpki-root-certs` ([crates/engine/src/tls.rs#L61-L112](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/tls.rs#L61-L112)), preserving corporate/antivirus HTTPS inspection certs while covering missing Windows Update roots (like ISRG Root X1/X2 on older Windows 10). It also classifies TLS failures (`CertProblem`, [tls.rs#L140-L226](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/tls.rs#L140-L226)).
  - `posthaze-engine` uses `reqwest`'s `rustls-tls` feature ([Cargo.toml#L18](file:///e:/Development/posthaze-download-manager/Cargo.toml#L18)), which in `reqwest` 0.12 enables `webpki-roots` + `rustls-native-certs` via `hyper-rustls` ([Cargo.lock#L3510-L3514](file:///e:/Development/posthaze-download-manager/Cargo.lock#L3510-L3514)), but lacks `rustls-platform-verifier` dynamic store checks and structured certificate problem classification (`EngineError::Http` wraps all TLS errors generically).
- **Redirects & Credential Scoping:**
  - `mdm-engine` raises redirect cap to `MAX_REDIRECTS = 20` ([download.rs#L729](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L729)) and implements `scoped_headers()` ([download.rs#L680-L696](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L680-L696)) to strip `Cookie`, `Authorization`, and `Proxy-Authorization` on cross-host hops or HTTPS→HTTP downgrades while preserving cookies across `sites::same_party` hops (`get_policy`, [download.rs#L734-L745](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L734-L745)).
  - `posthaze-engine` uses `reqwest`'s default redirect limit (10) and standard `apply_custom_headers()` ([probe.rs#L14-L36](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/probe.rs#L14-L36)), which forwards custom headers directly onto every `client.get(final_url)` call after probing. Note: if a redirect changed hosts between `probe()` and transfer, Posthaze still sends the original `request.headers` (including any `Cookie` / `Authorization`) to `probe.final_url`.

### 3.4 Retries, `Retry-After`, Rate Limiting, Learned Host Caps, and Link Refresh

- **`429` / `503` `Retry-After` & Backoff:**
  - `mdm-engine` parses `Retry-After` (both integer seconds and HTTP-dates, capped at `300s`) into `Error::Throttled(status, Option<Duration>)` ([crates/engine/src/download.rs#L386-L387, #L571-L578, #L655-L657, #L6174-L6184](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L571-L578)). For non-throttled transient errors, the **first retry is immediate** (matching IDM), then doubles from `retry_delay` (`1s`) up to `30s`.

## 4. Deep Comparison: Worker Handling

### 4.1 Segment Allocation, Dynamic Splitting, and Preemption

- **Initial Allocation & Small/Medium Files:**
  - `posthaze-engine` uses `MIN_SEGMENT_SIZE = 2 MiB` ([crates/posthaze-engine/src/transfer.rs#L18](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L18)) in `plan_segments()` ([transfer.rs#L99-L117](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L99-L117)): `count = (total_bytes / 2 MiB).max(1).min(max_workers)`. Consequently, any file `< 4 MiB` runs on **1 worker**, and a `10 MiB` file maxes out at 5 workers.
  - `mdm-engine` starts with `[0, size)` in `Planner` ([crates/engine/src/planner.rs#L90-L102](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/planner.rs#L90-L102)), spawns `min(max_connections, size.div_ceil(INITIAL_PIECE))` workers (`INITIAL_PIECE = 64 KiB`, [download.rs#L78, #L4202-L4204](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L4202-L4204)), and lets workers bisect dynamically down to `min_split = 12 KiB` (`ALIGN = 4096` boundary alignment, [planner.rs#L20, #L213-L236](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/planner.rs#L213-L236)).
  - **Impact on tail latency:** In Posthaze, if 1 of 8 workers gets stuck on a slow socket with `1.9 MiB` remaining (`<= MIN_SEGMENT_SIZE`), the other 7 workers finish and sit idle ([transfer.rs#L488-L490](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L488-L490)). MDM keeps splitting down to `12 KiB` (page-aligned at `4096 B`) so fast workers finish the tail in parallel.
- **Hot-Path Synchronization Overhead on Splits:**
  - In Posthaze, `steal_largest_segment()` ([transfer.rs#L474-L511](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L474-L511)) is pure in-memory, **but** immediately afterward both `execute_multi_segment_from_checkpoints()` ([transfer.rs#L304-L316](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L304-L316)) and `run_worker_loop()` ([transfer.rs#L438-L450](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L438-L450)) **await `store.split_segment(...).await?`** (a full SQLite transaction in [store.rs#L494-L528](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/store.rs#L494-L528)) *before* the idle worker can send its next HTTP `Range` request. If Posthaze lowers `MIN_SEGMENT_SIZE` to e.g. `256 KiB`, synchronous SQLite transactions per split would add noticeable latency on high-speed transfers.
  - In MDM, `Planner::assign()` splits strictly in-memory under a fast `Mutex` ([download.rs#L4295](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L4295)), and the periodic saver snapshots `planner.save()` on its own schedule ([download.rs#L3409](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L3409)).
- **Adjacent Slow-Start Preemption:**
  - `Planner::assign()` rule 2 ([planner.rs#L198-L210](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/planner.rs#L198-L210)) checks if the adjacent segment right after the one a worker just finished still has `!s.receiving` after `preempt_after = max(probe_ttfb * 2, 20ms)` ([download.rs#L81-L82, #L2394](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L2394)). If so, the warm worker takes over that segment and the stalled worker receives `Claim::Lost` on its first chunk. Posthaze has no equivalent preemption for slow TCP/TLS handshakes.

### 4.2 Worker Failure Isolation

- **`misterdownloadmanager` (Fault-Tolerant):**
  - When a worker hits a non-fatal error (exhausts `max_retries`, receives `link_dead()`, or hits `HostLimits`), `worker()` releases its segment back to `Planner` and exits with `Ok(())` **as long as `p.active_workers() > 0`** ([crates/engine/src/download.rs#L4374-L4437](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L4374-L4437)). The surviving workers automatically pick up the unassigned segment via `Planner::assign()` rule 1 ([planner.rs#L188-L196](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/planner.rs#L188-L196)).
  - In `supervise()` ([download.rs#L4257-L4263](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L4257-L4263)), if `set.is_empty()` while the download is still incomplete, it only fails if `last_err` was fatal/exhausted; otherwise it respawns a worker.
- **`posthaze-engine` (All-or-Nothing Abort):**
  - In `execute_multi_segment_from_checkpoints()` ([crates/posthaze-engine/src/transfer.rs#L366-L384](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L366-L384)), if **any single worker** returns `Err(err)`, the coordinator immediately calls `join_set.abort_all()` and fails the entire download—even when 7 other workers are transferring cleanly.

### 4.3 Pause, Cancellation, and Runtime Tuning

- **Posthaze's Pause/Cancel & Runtime Hygiene Are Stronger:**
  - Posthaze uses `watch::Receiver<ControlSignal>` (`Run | Pause | Cancel`). On `Pause`, workers flush their active `PooledBuffer`s into `PartFileWriter`, `flush_and_close()` drains the bounded channel and returns exact writer-acknowledged segment offsets, and `store.finalize_writer_checkpoint()` atomically commits them to SQLite ([runner.rs#L853-L902](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/runner.rs#L853-L902)). On `Cancel`, `writer.abort()` stops immediately without draining ([runner.rs#L904-L917](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/runner.rs#L904-L917)).
  - Posthaze also caps its Tokio runtime in `EngineBridge::open()` (`worker_threads = cores.clamp(2, 4)`, `max_blocking_threads(16)`, `thread_keep_alive(5s)`, [crates/posthaze-ui/src/bridge.rs#L74-L86](file:///e:/Development/posthaze-download-manager/crates/posthaze-ui/src/bridge.rs#L74-L86)), whereas MDM uses `tokio::runtime::Runtime::new()` ([crates/app/src/main.rs#L508](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/app/src/main.rs#L508)) spawning 1 worker thread per logical core and up to 512 blocking threads.

#### Critical Speed Finding: NTFS Zero-Fill Stall Without `FSCTL_SET_SPARSE`
In [crates/posthaze-engine/src/writer.rs#L300-L302](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/writer.rs#L300-L302), Posthaze calls `file.set_len(len)` on a non-sparse NTFS file, then immediately dispatches workers writing at offsets `len/8`, `len/4`, ..., `7*len/8`. As documented in `mdm-engine`'s [crates/engine/src/sparse.rs#L3-L11](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/sparse.rs#L3-L11), NTFS synchronously zero-fills all unwritten bytes up to the highest write offset when extending a non-sparse file's valid data length (MDM measured **4.3 seconds for a single 1 MiB write at 2 GiB**, doubling total disk write traffic). Marking the `.part` file sparse (`FSCTL_SET_SPARSE`) prior to `set_len(len)` for files `>= 5 MiB`—and clearing sparse before the final rename (`sparse::set(&file, false)` before `sync` / `rename`)—eliminates this startup stall completely.

### 5.3 Bandwidth Limiter / Throttling Overhead

- Both engines share an atomic `rate == 0` fast-path (`limiter.rs#L113-L115`, `throttle.rs#L42-L45`) so unlimited downloads incur **zero mutex/sleep overhead**.

## 6. Where Posthaze Is Already Stronger (Do Not Regress)

1. **Deterministic, Low-RAM Write Pipeline (`16 MiB` vs. `256 MiB`):**
   - `PartFileWriter` + `ChunkBufferPool` ([writer.rs#L25-L132](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/writer.rs#L25-L132)) bounds in-flight payload memory to `16 MiB` per download with zero steady-state chunk heap allocations, compared to MDM's `256 MiB` `HOLD_MAX` + per-worker `4 MiB` `spare` pools ([download.rs#L43, #L53](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L53)).
2. **Pipelined Single-Stream Disk I/O:**
   - Posthaze's `execute_single_stream()` ([transfer.rs#L790-L843](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L790-L843)) coalesces small HTTP chunks into `512 KiB` `PooledBuffer`s and writes asynchronously via `PartFileWriter`. MDM's `single_stream()` ([download.rs#L6095-L6098](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L6095-L6098)) awaits `spawn_blocking` synchronously on *every single HTTP chunk*.
3. **Zero Blocking-Pool Task Churn on Multi-Segment Writes:**
   - Posthaze uses **1 persistent blocking thread** per active download ([writer.rs#L352](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/writer.rs#L352)), whereas MDM calls `tokio::task::spawn_blocking` for every `<= 4 MiB` write batch per worker and every `read_at` overlap check ([download.rs#L5536, #L5838](file:///C:/Users/prage/.gemini/antigravity/brain/68f916d5-a49d-44b1-b60f-1a921a1da2d5/scratch/misterdownloadmanager/crates/engine/src/download.rs#L5838)).
4. **Shared Warm `reqwest::Client` & Bounded Tokio Runtime:**
   - Posthaze reuses its `reqwest::Client` across downloads unless proxy settings change ([lib.rs#L509-L530](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/lib.rs#L509-L530)) and bounds `EngineBridge` to `2..=4` Tokio workers + `16` max blocking threads ([bridge.rs#L75-L85](file:///e:/Development/posthaze-download-manager/crates/posthaze-ui/src/bridge.rs#L75-L85)).
5. **Centralized SQLite WAL Persistence & Clean Engine/UI Decoupling:**
   - `DownloadEngine` maintains full queue history, settings, and crash-reconciled segment state in SQLite WAL (`synchronous = NORMAL`, `PRAGMA shrink_memory`) with structured `EngineEvent` broadcasts ([store.rs#L121-L167, #L531-L560](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/store.rs#L121-L167)) rather than per-file `.mdm.json` sidecars + `sync_data()` flushes on disk.
6. **Engine-Owned Strict FIFO Queue Coordinator:**
   - `QueueCoordinator` ([queue.rs#L20-L134](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/queue.rs#L20-L134)) provides RAII slot accounting and deterministic FIFO concurrency admission inside the engine rather than UI polling.

## 7. Concrete Implementation & Verification Notes for Top Priorities

1. **NTFS Sparse `.part` Preallocation (P0):**
   - In `PartFileWriter::spawn_with_checkpoint()` ([writer.rs#L300-L302](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/writer.rs#L300-L302)), before `file.set_len(len)` when `len >= 5 * 1024 * 1024`, issue `DeviceIoControl(..., FSCTL_SET_SPARSE, &FILE_SET_SPARSE_BUFFER { SetSparse: 1 }, ...)` on `#[cfg(windows)]` (requires `Win32_System_IO` / `Win32_System_Ioctl` features in `windows-sys`). Clear sparse (`SetSparse: 0`) inside `PartFileWriter::finish()` before closing/renaming so the completed file has normal NTFS attributes.
2. **HTTP Read Timeout & Explicit HTTP/1.1 Guard (P0/P1):**
   - In `build_http_client()` ([lib.rs#L684-L689](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/lib.rs#L684-L689)), add `.read_timeout(Duration::from_secs(30))` and `.http1_only()`.
3. **Worker Failure Isolation & `Retry-After` (P0):**
   - In `execute_multi_segment_from_checkpoints()` ([transfer.rs#L366-L384](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L366-L384)), only abort remaining workers on `Paused`, `Cancelled`, `Writer(_)`, or non-retryable fatal errors (`ResourceChanged`, `UnexpectedHtmlResponse`). If a worker exhausts `MAX_SEGMENT_RETRIES` on a transient/403/connection error while `active_workers > 1` (tracked after decrement), release its segment (`claimed.store(false, Ordering::Release)`) so surviving workers claim it via `claim_unclaimed_segment()` ([transfer.rs#L462-L472](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L462-L472)); only fail the download if the *last* worker exits with an error.
   - Add `Retry-After` header parsing to `EngineError::HttpStatus` (or a dedicated `Throttled { status, retry_after, url }` variant) for `429` / `503` and honor it in `run_segment_worker()` ([transfer.rs#L569](file:///e:/Development/posthaze-download-manager/crates/posthaze-engine/src/transfer.rs#L569)), capped at e.g. `300s`.
4. **Slow-Worker Shedding + Decoupled Segment Splitting (P1):**
   - Move `store.split_segment(...)` off the worker critical path (record splits in memory and upsert segments on the periodic `spawn_checkpoint_task` / pause finalizer) so `MIN_SEGMENT_SIZE` can safely drop from `2 MiB` to `256 KiB`–`512 KiB` (`4 KiB`-aligned) without SQLite round-trips stalling workers.
   - Track per-worker network pace excluding `PartFileWriter` channel wait time (mirroring MDM's `Pace::on_disk`) and reconnect stragglers `< shed_bar / 4` after `2s` grace when `> 2s` remains and `BandwidthLimiter` is inactive.
5. **Verification Plan:**
   - Benchmark before/after with `cargo bench -p posthaze-engine` and `posthaze-cli bench --sizes 100M,1G -c 1,4,8,16,32 --no-external --compare-db`, plus flaky/throttled simulation (`--per-conn-mbps 40 --drop-pct 5 --error-503-pct 5`) and large-file NTFS creation latency on a real Windows non-OS HDD/NVMe drive.
